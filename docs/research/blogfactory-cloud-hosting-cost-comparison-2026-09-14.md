# BlogFactory Cloud hosting cost comparison — 2026-09-14

## Decision

Use the existing **Hetzner CX23 in Nuremberg + Neon Frankfurt + R2** for Phases A and B while it passes the plan's latency, queue, memory, and CPU gates. It preserves the already-built Docker/Compose topology and a real persistent five-second Bun worker without a platform rewrite. The account screenshot shows a retained **$4.99/month** server price; with a $0.60 primary IPv4 and backups at 20%, the VM side is about **$6.59/month pre-tax**. Neon Free is initially $0; budgeting Neon's published $15 typical Launch usage for the temporary PITR exercise gives a conservative total of about **$21.59/month**, with R2 inside its free allowance.

Do not resize to CPX22 pre-emptively. A new-order CPX22 is $22.99 before IPv4 and backups, making the conservative stack about **$43.19/month** and leaving only $1.81 below the Phase B ceiling. Upgrade only if CX23 measurements fail a resource gate.

This is a hosting recommendation, not authority to create an account, VM, DNS record, or paid resource.

## Scope and costing method

- Workload: Vite static web, Hono/Bun API, one continuously running worker that polls PostgreSQL every five seconds, separate Neon Frankfurt PostgreSQL, and R2 object storage. The repository's worker mode is intentionally persistent; five-minute cron and request-scoped functions do not satisfy it.
- Amounts are public list prices checked on 2026-09-14, pre-tax, rounded to cents. Provider prices are mixed USD/EUR; Hetzner's published USD Germany figures are used for the two budget totals. Neon is common to every candidate and its $15 is a published *typical* Launch spend, not a floor or quote.
- R2's $0 pilot assumption means no more than 10 GB-month Standard storage, 1M Class A, and 10M Class B operations. It does not mean object traffic is unmetered: operations are billable above those allowances.
- A single process handles API and worker on the smallest VM/Machine candidates. That is appropriate only while the process has resource headroom and database-backed claims/stale recovery remain correct; it is not HA.

## What not to build

- Do not build a second scheduler just to fit Vercel, Netlify, or Workers. PostgreSQL claims, stale recovery, bounded retries, and the one existing persistent worker already cover the required queue model.
- Do not colocate PostgreSQL or object storage on the VM merely to reduce the displayed hosting bill. Neon Frankfurt and R2 are intentional separate data boundaries.
- Do not promise five-second execution from any cron/alarm product. The worker's poll interval is an application target, not a platform scheduling SLA.
